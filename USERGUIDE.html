dev

Ambiente de desenvolvimento PHP e Node.js para WSL2 e Linux, sem Docker e modular por plugins.

1. Visão Geral e Arquitetura

O dev foi projetado para alta velocidade, determinismo e simplicidade operacional:

  • Core Principal: Instala PHP 8.5 estático, Nginx 1.30 estático, MySQL 8.4 LTS, Node.js LTS, Composer, Mailpit, Adminer e autoridade local mkcert.
  • Arquitetura de Plugins: Aplicações pesadas (WordPress, Laravel, Moodle) não poluem o core. Instale incrementalmente apenas o que você precisa.
  • Sem Docker nem systemd: Inicialização instantânea em segundos, baixo consumo de memória e supervisão inteligente de portas.

3. Sistema Modular de Plugins

Gerencie o ciclo de vida dos plugins com facilidade:

na máquina

$ dev plugin list ✔ wordpress WordPress instalado ○ laravel Laravel disponível ○ moodle Moodle disponível $ dev plugin install moodle ✔ plugin "moodle" instalado com sucesso $ dev plugin update ✔ moodle atualizado ✔ wordpress já está em dia $ dev plugin remove laravel ✔ plugin "laravel" removido com sucesso

O dev plugin update traz a versão atual da receita e das notas do agente para um plugin já instalado, sem tocar nos projetos. Depois dele, dev agent update regenera as skills com as notas novas.

7. Testes da Aplicação

Cada aplicação traz as suítes de teste oficiais dela. O dev test as roda com o PHP, o Node, o Composer e o banco do projeto. A primeira execução prepara a suíte; os testes usam tabelas e diretórios próprios e não tocam nos dados do site.

AplicaçãoSuíteO que roda
MoodlephpunitPHPUnit do Moodle, tabelas phpu_ e dados em data-phpunit/. Caminhos relativos a app/
MoodlebehatBehat no Chrome do dev, tabelas bht_, dados em data-behat/ e site em https://test.<projeto>.localhost
Laravelpest ou phpunitphp artisan test; o nome segue o que o projeto usa
LaravelbrowserTestes de navegador do Pest 4 (pestphp/pest-plugin-browser); o Pest serve a aplicação sozinho
WordPressphpunitTestes de integração de um plugin ou tema com a biblioteca oficial do WordPress, no banco <banco>_tests
WordPresse2ePlaywright do projeto (@playwright/test), logado com um usuário temporário criado só para a execução

no diretório do projeto

$ dev test TESTES meu-ead phpunit testes unitários e de integração (PHPUnit; tabelas phpu_, dados em data-phpunit/) behat testes de aceitação no navegador (Behat + Chrome em https://test.meu-ead.localhost) $ dev test phpunit --filter=meu_teste $ dev test behat --tags=@local_meuplugin $ dev test init behat ✔ behat pronta

Depois de atualizar a aplicação, instalar um plugin ou criar passos novos do Behat, rode dev test init <suíte>.

Qual navegador cada suíte usa

O Behat do Moodle fala WebDriver, que exige um chromedriver da mesma versão do Chrome. Por isso o dev fixa os dois juntos: Chrome for Testing com sha256 conferido no download (dev browser install, ou automaticamente na primeira execução). O e2e do WordPress e o navegador do Pest usam o Playwright do próprio projeto, que baixa o build que aquela versão dele fixa. Desde o Playwright 1.57 esse build também é um Chrome for Testing; só muda quem fixa a versão. Os dois ficam em ~/.dev/runtime, compartilhados entre projetos.

As bibliotecas do sistema que o Chrome pede são oferecidas para instalação via sudo apt. Se o sistema bloquear o sandbox do Chrome, BROWSER_NO_SANDBOX=1 em ~/.dev/config o desliga.

Usuário de teste temporário

Para testar no navegador sem usar a conta de administrador real, o dev test user cria a conta devtest e mostra a senha. Cada chamada troca a senha. A conta some no dev down ou com dev test user --remove. Um usuário devtest que o dev não criou nunca é alterado.

no diretório do projeto

$ dev test user USUÁRIO DE TESTE meu-ead login devtest senha DevKxwPqrTmab7# papel administrador do site site https://meu-ead.localhost → conta temporária: some no dev down, ou já com: dev test user --remove $ dev test user --no-admin $ dev test user --remove

8. Agentes de IA e Navegador do Agente

O dev agent add gera a skill do dev no projeto para Claude Code, Codex ou Antigravity. Ela ensina o agente a rodar tudo pelo dev, a usar o dev test e a testar no navegador com o usuário temporário, nunca com o administrador real.

Com --browser, o agente ganha também um navegador: o Playwright MCP, em versão fixada, com o Chrome do dev, sem janela e sem perfil em disco. Ele só alcança https://<projeto>.localhost, https://test.<projeto>.localhost e o Mailpit. O Playwright avisa que essa lista não é uma barreira de segurança, então trate-a como proteção contra engano, não contra código malicioso.

no diretório do projeto

$ dev agent add claude --browser ✔ claude .claude/skills/dev/SKILL.md ✔ Chrome for Testing 157.0.8103.38 com chromedriver ✔ Playwright MCP 0.0.83 ✔ claude .mcp.json servidor dev-browser
AgenteOnde o navegador é configurado
Claude Code.mcp.json na raiz do projeto; outros servidores do arquivo são preservados. O Claude Code pede aprovação antes de ativar.
Codex.codex/config.toml do projeto, num bloco marcado; o Codex só o lê em projetos confiáveis
AntigravitySó aceita MCP na configuração global; o dev mostra o trecho para colar

A configuração gravada só chama dev browser mcp <projeto>: não leva senha nem caminho da máquina e pode ir para o git. O dev agent remove tira a skill e a entrada do navegador; o dev browser remove apaga o Chrome e o Playwright MCP da máquina.

Documentação atualizada (Context7)

Com --docs, o agente ganha o servidor dev-docs: o Context7 MCP, em versão fixada, que entrega a documentação atual de Laravel, WordPress, Moodle e das bibliotecas do projeto. A skill passa a dizer a versão instalada da aplicação e os IDs do Context7 que valem para ela, para que o agente consulte a documentação daquela versão antes de escrever código.

na máquina

$ dev docs key ? chave de API do Context7 (não aparece ao digitar): ✔ chave aceita pelo Context7 ✔ chave gravada em ~/.dev/config ctx7sk-…a1b2

no diretório do projeto

$ dev agent add claude --docs ✔ claude .claude/skills/dev/SKILL.md ✔ Context7 MCP 4.4.4 ✔ claude .mcp.json servidor dev-docs
AplicaçãoIDs do Context7 na skill
Laravel/laravel/docs/<major>.x, /laravel/framework, /pestphp/docs
WordPressReferência de funções, hooks e classes, Plugin e Theme Handbooks, /wordpress/gutenberg, /wp-cli/handbook
Moodle/websites/moodledev_io, /moodle/devdocs, /moodle/moodle

A chave fica em ~/.dev/config (permissão 600), ou na variável CONTEXT7_API_KEY, que tem precedência. A configuração do projeto só chama dev docs mcp, que entrega a chave ao servidor por variável de ambiente: ela não vai para o projeto, para o git nem para a linha de comando. Sem chave, o Context7 funciona com limites de uso menores. Com a chave gravada, dev new --agent <alvo> já inclui a documentação. Depois de atualizar a aplicação, rode dev agent update para a skill trazer a versão nova.
