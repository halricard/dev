dev

Ambiente de desenvolvimento PHP e Node.js para WSL2 e Linux, sem Docker e modular por plugins.

1. Visão Geral e Arquitetura

O dev foi projetado para alta velocidade, determinismo e simplicidade operacional:

  • Core Principal: Instala PHP 8.5 estático, Nginx 1.30 estático, MySQL 8.4 LTS, Node.js LTS, Composer, Mailpit, Adminer e autoridade local mkcert.
  • Arquitetura de Plugins: Aplicações pesadas (WordPress, Laravel, Moodle) não poluem o core. Instale incrementalmente apenas o que você precisa.
  • Sem Docker nem systemd: Inicialização instantânea em segundos, baixo consumo de memória e supervisão inteligente de portas.

3. Sistema Modular de Plugins

Gerencie o ciclo de vida dos plugins com facilidade:

na máquina

$ dev plugin list ✔ wordpress WordPress instalado ○ laravel Laravel disponível ○ moodle Moodle disponível $ dev plugin install moodle ✔ plugin "moodle" instalado com sucesso $ dev plugin update ✔ moodle atualizado ✔ wordpress já está em dia $ dev plugin remove laravel ✔ plugin "laravel" removido com sucesso

7. Testes da Aplicação

Cada aplicação traz as suítes de teste oficiais dela. O dev test as roda com o PHP, o Node, o Composer e o banco do projeto. A primeira execução prepara a suíte; os testes usam tabelas e diretórios próprios e não tocam nos dados do site.

AplicaçãoSuíteO que roda
MoodlephpunitPHPUnit do Moodle, tabelas phpu_ e dados em data-phpunit/. Caminhos relativos a app/
MoodlebehatBehat no Chrome do dev, tabelas bht_, dados em data-behat/ e site em https://test.<projeto>.localhost
Laravelpest ou phpunitphp artisan test; o nome segue o que o projeto usa
LaravelbrowserTestes de navegador do Pest 4 (pestphp/pest-plugin-browser); o Pest serve a aplicação sozinho
WordPressphpunitTestes de integração de um plugin ou tema com a biblioteca oficial do WordPress, no banco <banco>_tests
WordPresse2ePlaywright do projeto (@playwright/test), logado com um usuário temporário criado só para a execução

no diretório do projeto

$ dev test TESTES meu-ead phpunit testes unitários e de integração (PHPUnit; tabelas phpu_, dados em data-phpunit/) behat testes de aceitação no navegador (Behat + Chrome em https://test.meu-ead.localhost) $ dev test phpunit --filter=meu_teste $ dev test behat --tags=@local_meuplugin $ dev test init behat ✔ behat pronta

Depois de atualizar a aplicação, instalar um plugin ou criar passos novos do Behat, rode dev test init <suíte>.

Qual navegador cada suíte usa

O Behat do Moodle fala WebDriver, que exige um chromedriver da mesma versão do Chrome. Por isso o dev fixa os dois juntos: Chrome for Testing com sha256 conferido no download (dev browser install, ou automaticamente na primeira execução). O e2e do WordPress e o navegador do Pest usam o Playwright do próprio projeto, que baixa o build que aquela versão dele fixa. Desde o Playwright 1.57 esse build também é um Chrome for Testing; só muda quem fixa a versão. Os dois ficam em ~/.dev/runtime, compartilhados entre projetos.

As bibliotecas do sistema que o Chrome pede são oferecidas para instalação via sudo apt. Se o sistema bloquear o sandbox do Chrome, BROWSER_NO_SANDBOX=1 em ~/.dev/config o desliga.

Usuário de teste temporário

Para testar no navegador sem usar a conta de administrador real, o dev test user cria a conta devtest e mostra a senha. Cada chamada troca a senha. A conta some no dev down ou com dev test user --remove. Um usuário devtest que o dev não criou nunca é alterado.

no diretório do projeto

$ dev test user USUÁRIO DE TESTE meu-ead login devtest senha DevKxwPqrTmab7# papel administrador do site site https://meu-ead.localhost → conta temporária: some no dev down, ou já com: dev test user --remove $ dev test user --no-admin $ dev test user --remove

8. Claude Code: Skill e Ferramentas

O dev agent add gera só a skill do dev para o Claude Code, em .claude/skills/dev/SKILL.md. Ela ensina o Claude Code a rodar tudo pelo dev, a usar o dev test e a testar no navegador com o usuário temporário, nunca com o administrador real. Cada ferramenta é opcional e entra por uma flag com o nome dela:

No final, a seção "PARA TERMINAR A CONFIGURAÇÃO" mostra o que depende de você em cada ferramenta instalada: a chave opcional do Context7, o login do Figma, o token do GitHub e o /impeccable init, que o próprio Claude Code roda na primeira tela se você não o adiantar.

A skill descreve só as ferramentas presentes no projeto, cada uma com as fases em que entra: contexto, especificar, desenhar, tarefas, executar, verificar e entregar. Ela traz também as notas de UI da aplicação, que o Figma e o impeccable seguem para a tela parecer parte do Moodle, do WordPress ou do Laravel. O dev detecta as ferramentas no .mcp.json e em .claude/skills, então o dev agent update acompanha o que foi instalado ou tirado depois.

Navegador (Playwright)

O navegador só alcança https://<projeto>.localhost, https://test.<projeto>.localhost e o Mailpit. O Playwright avisa que essa lista não é uma barreira de segurança, então trate-a como proteção contra engano, não contra código malicioso. O dev browser remove apaga o Chrome e o Playwright MCP da máquina.

Documentação atualizada (Context7)

A skill passa a dizer a versão instalada da aplicação e os IDs do Context7 que valem para ela, para que o Claude Code consulte a documentação daquela versão antes de escrever código.

na máquina

$ dev agent key context7 ? chave de API do Context7 (não aparece ao digitar): ✔ chave aceita pelo Context7 ✔ chave gravada em ~/.dev/config ctx7sk-…a1b2
AplicaçãoIDs do Context7 na skill
Laravel/laravel/docs/<major>.x, /laravel/framework, /pestphp/docs
WordPressReferência de funções, hooks e classes, Plugin e Theme Handbooks, /wordpress/gutenberg, /wp-cli/handbook
Moodle/websites/moodledev_io, /moodle/devdocs, /moodle/moodle

A chave fica em ~/.dev/config (permissão 600), ou na variável CONTEXT7_API_KEY, que tem precedência. O servidor do projeto só chama dev context7 mcp, que entrega a chave por variável de ambiente: ela não vai para o projeto, para o git nem para a linha de comando. Sem chave, o Context7 funciona com limites de uso menores.

Chaves (Context7, GitHub e Penpot)

As chaves ficam num lugar só: ~/.dev/config, com permissão 600. O dev agent key pede a chave sem mostrá-la, confere no serviço e a grava; sem ferramenta, mostra as chaves gravadas, mascaradas. Os servidores dev-context7 e github são iniciados pelo próprio dev, que entrega a chave por variável de ambiente: ela não vai para o projeto, para o git nem para a linha de comando. Uma variável de ambiente com o mesmo nome (CONTEXT7_API_KEY, GITHUB_PAT) vence a chave gravada.

O Penpot é a exceção: o servidor dele só aceita a chave na URL, que o Claude Code monta a partir do próprio ambiente. Para ele, o dev agent key penpot também mantém no ~/.bashrc um bloco marcado que lê a chave de ~/.dev/config a cada terminal novo; o bloco não guarda a chave e sai com dev agent key penpot --remove. Depois de gravar, abra um terminal novo antes de abrir o Claude Code.

na máquina

$ dev agent key github ? token do GitHub (não aparece ao digitar): ✔ aceita pelo GitHub ✔ gravada em ~/.dev/config github_…wxyz $ dev agent key CHAVES DAS FERRAMENTAS ✔ context7 ctx7sk-…a1b2 em ~/.dev/config ✔ github github_…wxyz em ~/.dev/config ○ penpot não gravada crie em Penpot → Your account → Integrations → MCP Server

O GitHub é um servidor remoto. O dev o alcança pelo mcp-remote, em versão fixada, que faz a ponte entre o Claude Code e o servidor. Crie um token fine-grained em https://github.com/settings/personal-access-tokens, com acesso aos repositórios do projeto e Contents, Issues e Pull requests em Read and write. Se o Claude Code já estiver aberto quando você gravar o token, reconecte o servidor em /mcp.

Figma

O servidor remoto do Figma não usa chave: pede login uma vez, no Claude Code. Rode /mcp, escolha figma e depois Authenticate.

Penpot

O Penpot é a alternativa de código aberto ao Figma, e o projeto usa um dos dois: --figma e --penpot juntos são recusados, e instalar um tira o servidor do outro. O servidor MCP oficial do Penpot é remoto e autentica por uma chave pessoal na própria URL. Gere a chave em Your account → Integrations → MCP Server (ela aparece uma vez só) e grave-a com dev agent key penpot. Para um Penpot próprio, exporte também PENPOT_URL; o padrão é https://design.penpot.app. O .mcp.json guarda só as referências às duas variáveis.

O servidor age pelo plugin MCP do Penpot no navegador: abra um arquivo de design, use File → MCP Server → Connect e deixe a aba aberta enquanto o Claude Code trabalha. Além de ler pranchas, o Claude Code pode desenhar um rascunho de tela no arquivo aberto antes de escrever código, quando você pedir.

impeccable e TLC

Os dois vêm dos instaladores oficiais (npx impeccable install e npx @tech-leads-club/agent-skills install), rodados com o Node do dev, sempre na versão atual: o dev não fixa a versão deles. Os instaladores rodam sem perguntas, só para o Claude Code, numa pasta temporária; só a skill e os subagentes que ela traz (.claude/agents) vêm para o projeto. Assim nada é gravado para outros agentes nem num repositório git acima do projeto. O impeccable entra sem os hooks do detector de design: a skill do dev diz em que fases usar cada comando dele. Com o TLC, o CLAUDE.md do projeto ganha um bloco marcado que manda o Claude Code carregar a skill do dev antes de cada fase; o resto do arquivo nunca é alterado. Só um método por projeto.

Nenhum arquivo gravado no projeto leva senha, chave, token ou caminho da máquina, então todos podem ir para o git. O Claude Code pede aprovação antes de ativar os servidores do .mcp.json. O dev agent remove tira a skill, os servidores e o bloco do CLAUDE.md gerados pelo dev; o TLC e o impeccable continuam em .claude/skills.
